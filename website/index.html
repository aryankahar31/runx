The wedge

A fresh laptop, a locked-down work machine, a CI runner. Same project works.

No admin rights

Runtimes are downloaded to ~/.runx as portable vendor binaries. Nothing is installed system-wide, nothing needs sudo.

No global installs

Node 18, Node 22 and Python 3.12 can coexist per project. Your system toolchains stay untouched.

No shell hooks

No eval in your profile, no shims, no per-prompt cost. Nothing runs until you type runx.

No new config file required

It reads what the repo already declares. runx.toml is optional and always wins when present.

01 — How it works

One command. Six explicit steps.

No hidden daemon, no ambient state. runx dev resolves what the project needs, verifies it, builds a child-only PATH, and executes.

  1. 01

    Parse

    Read runx.toml, or detect from project files.

  2. 02

    Resolve

    Exact pins or semver ranges, against vendor indexes.

  3. 03

    Cache

    Hot cache: reuse ~/.runx/runtimes. Miss: install.

  4. 04

    Download + verify

    Staged download, SHA-256 checked before extraction.

  5. 05

    Isolate

    Build a child-process PATH with the exact runtimes.

  6. 06

    Execute

    Start your command. Your shell never changes.

Detection is a collection, not a winner

A project can need Node for the front end and Python for tooling. runx resolves all of them into one isolated environment, so even child processes find the right binaries.

Explicit config always wins

If runx.toml exists, detection is skipped entirely — no merging, no surprises. Without it, every package.json script becomes a run command.

Reproducible when you need it

runx lock records exact versions and per-platform digests. --locked enforces them in CI, including cached archive integrity.

runx.toml — optional 
[runtimes]
node = "20.11.0"
python = "3.11.7"

[run]
dev = "npm run dev"
build = "npm run build"
test = "npm test"

02 — Quick start

Install in one line. Verify it if you want.

One static binary. No admin rights, no system dependencies. The installer verifies the download against its published SHA-256 before installing, and aborts on mismatch.

curl -fsSL https://raw.githubusercontent.com/aryankahar31/runx/main/install.sh | sh

Installs to ~/.runx/bin and offers — once — to add that directory to your shell PATH. No hooks, no shims, no runtime switching.

Trust, visible

Verify the release yourself

Every install script checks the archive's published SHA-256. Since v0.4.2, release archives and SHA256SUMS are also signed with Sigstore/cosign keyless signing.

sha256sum -c SHA256SUMS --ignore-missing
Verify the Sigstore signature (cosign)
cosign verify-blob SHA256SUMS \ --bundle SHA256SUMS.sigstore.json \ --certificate-identity-regexp '^https://github\.com/aryankahar31/runx/\.github/workflows/release\.yml@refs/(tags/v[0-9]+\.[0-9]+\.[0-9]+|heads/main)$' \ --certificate-oidc-issuer https://token.actions.githubusercontent.com
runx doctor --verify

Set RUNX_REQUIRE_SIGNATURE=1 to fail closed when cosign or a signature is missing.

04 — Security & verification

Downloads are verified. Limits are documented.

runx pulls official vendor binaries, checks them, and tells you exactly what each layer does — including the gaps.

01

SHA-256 before extraction

Archive checksums are fetched from the vendor and verified before anything is unpacked. Older Deno releases (1.x and 2.0.0) publish no archive checksum; runx installs them TLS-only and warns.

02

Sigstore/cosign on runx releases

Since v0.4.2, runx's own archives and SHA256SUMS are signed with keyless Sigstore. Installers and self update verify the signature when cosign is present. Vendor runtimes are not signed by runx.

03

Lockfile digests, not trust

A recorded per-platform artifact digest becomes the install constraint. --locked verifies retained archives and compares cached contents with a fresh extraction. Missing metadata or mismatched bytes abort.

04

Isolated child PATH

Each invocation computes a child-only PATH from resolved runtimes. Your shell environment is never mutated, and a probe-process regression test asserts that.

05

No telemetry

runx makes no requests beyond vendor release metadata, archives and checksums. The site sets no cookies and runs no analytics.

Limits

What it does not solve

Staged installs are verified before publication, but replacement is not crash-atomic. doctor --verify checks entry-point bytes against local receipts — not full-tree authentication. --locked is deliberately slow.

Verification details and manual checksum steps: docs/security.md.

Where runx is weaker

  • No ambient switching — you type runx; mise/asdf can switch as you cd.
  • No plugin ecosystem or registry; six runtimes, not hundreds.
  • Ruby, PHP, and .NET are planned, not shipped.
  • No monorepo/workspace support or pre/post hooks yet.
  • No Winget, Scoop, AUR, Nix, or Chocolatey packages yet (Winget, Scoop, AUR, and Nix are pending; Homebrew, Cargo, and npm are available).
  • Not a package manager: it does not install global CLIs or system libraries.
  • --locked costs seconds per run by design.

Any argument that is not a built-in subcommand is treated as a command key. Without runx.toml, every package.json script becomes a key. 

Usage: runx [OPTIONS] [COMMAND]

Pass arguments through with `--`:
  runx dev -- --port 3000

Use `runx run <key>` if a key collides with a built-in name.
runx run <key>Run a [run] command explicitly, with lockfile enforcement if asked. 
runx run test --locked
runx run dev --offline

           and verify cached runtime contents before execution.
runx initCreate a starter runx.toml from what runx detects.

Refuses to overwrite an existing config. Prints detected runtimes, package manager and inferred commands, then recommends the next command.

Usage: runx init [OPTIONS]
runx lockWrite runx.lock, pinning exact resolved versions and per-platform digests.

Installs declared runtimes if missing, then records what was resolved. Does not install project dependencies and does not start a command.

Usage: runx lock [OPTIONS]
runx installInstall project dependencies using the runx-managed runtime.

Detects the package manager from the lockfile: npm ci, yarn install, pnpm install, bun install, pip install -e . / -r requirements.txt, go mod download, deno install / deno cache. 

Usage: runx install [OPTIONS]

Does not start any command. Use `runx --install dev` to install then run.

Reports runtime, dependency and lockfile readiness with a pass/warn/fail reason and the command that resolves each issue. Exit code reflects cache health.

09 — FAQ

The honest questions.

Do I need admin rights or a system package manager?

No. The binary goes to ~/.runx/bin and runtimes to ~/.runx/runtimes. Override the cache with RUNX_HOME. Nothing is written outside your home directory.

Does it hook into my shell?

No. There is no eval line, no shim directory, no prompt hook. The installer may offer — once — to add ~/.runx/bin to PATH so you can type runx; that is ordinary PATH, not runtime switching.

Can I use it offline?

Cached runtimes work offline when the metadata runx needs is cached too. runx --offline dev refuses runx's network operations and names the missing prerequisite. It does not block your app's own network access.

Is runx a package manager?

No. It does not install global CLIs or system libraries. runx install runs the project's package manager using the managed runtime, and runx <script> runs project commands.

What happens if a runtime version does not exist?

runx reports that the version does not exist instead of surfacing a raw 404 against a URL. Range resolution picks the newest matching release from the vendor's index.

Why is --locked so slow?

It re-extracts each runtime archive and compares the cached tree, trusting no receipt. That is the point: it suits CI and release builds, not an edit-run loop. Expect seconds, not milliseconds.

Does it collect telemetry?

No telemetry, and this site sets no cookies and runs no analytics. GITHUB_TOKEN is optional and sent only to api.github.com to raise rate limits for Bun/Deno/Python lookups.

How do I uninstall?

Delete the binary (~/.runx/bin/runx or %USERPROFILE%\.runx\bin\runx.exe), then optionally remove ~/.runx and the PATH line the installer added.
